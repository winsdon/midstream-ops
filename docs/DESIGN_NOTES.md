# 口径与设计说明

本文记录 midstream-ops 各项数据口径的**定义、取舍与实现约束**。README 只回答「是什么、怎么跑」，本文回答「为什么这么算、为什么不那么算」。

看板上的每个数字都有一套口径，口径不写下来就会被各自默认地误读 —— 成本是不是含官价、分组利润为什么加起来偏高、色点为什么取最差而不是平均。这些都不是实现细节，是读数的前提。

## 账号归属供应商

账号属于哪个上游站点，由**显式关联表 `provider_accounts` 决定**，是收益/成本按供应商归并、探测按站点批量执行的唯一依据。

早期版本靠账号名的 `【站点名】` 前缀正则推导归属，已废弃 —— 账号改名会静默换归属让统计无声漂移，且无法表达「名字里没前缀但确实属于该站」。前缀规则本身保留，但**降级为「猜建议名」**：批量建站时据此预填站点名，省去逐个手打。

两个关联入口（供应商页）：

| 入口 | 适用 |
|------|------|
| 「扫描」→ 按站点地址 | 按账号实际连接的 `base_url` 归组多选，**不依赖任何命名习惯** |
| 「扫描」→ 按【】前缀 | 账号名带前缀时，一键批量建站并顺带关联该前缀下的全部账号 |
| 供应商行内「关联账号」 | 事后调整单个站点的关联集合（全量替换语义） |

- **一个账号只能属于一个站点**：勾选已属于别处的账号会把它转过来（收益统计里落两个桶会让合计翻倍）
- **未关联的账号归入「(未归属)」桶**：收益如实计入总计且看得见，不会被静默吞掉
- 删除站点时其关联被级联清除；远端账号被删后关联保留（便于排查），仅在展示时过滤

## 收益 / 成本 / 利润

| 指标 | 来源 | 说明 |
|------|------|------|
| **收益** | 本站 `usage_logs.actual_cost` 之和 | 用户实际扣费，即我们收到的钱。**恒为 CNY** |
| **成本（实扣）** | **上游 sub2api 的 per-key `actual_cost`** | 倍率折后实扣金额，即真正付给供应商的钱，参与利润计算。**自营站计 0**，见下 |
| **运营成本** | 手工录入的 `provider_operating_costs` | 自营站的买号 / 订阅 / 服务器等站外支出，参与利润计算。**按 CNY 录入** |
| **上游成本（对照）** | 上游 per-key `official_cost` | 未打折的上游对照价，**仅在供应商页 💰 成本明细里与实扣并列展示折扣节省，不参与利润** |
| **利润** | 收益 − 实扣成本 − 运营成本 | 三项同为 CNY 才可直接相减，见下「币种口径」 |

> 成本**不是**本站推算的，而是从上游供应商站点按 key 拉取的真实消耗。上游按 API key 计费，一个 key 对应本站一个账号，通过 key 指纹（回退账号名）匹配。**这与上面的「账号归属供应商」是两条独立链路**：前者决定钱算在哪个站头上，后者决定某笔实扣属于哪个账号。

### 币种口径（易错，改动前必读）

上游实扣**以各供应商自己的计价单位入库**：有的站按人民币计价，有的按 U（点数）计价。而收益恒为人民币。两者直接相减就是混算币种，利润会离谱到符号翻转。

因此所有成本聚合 SQL 都必须乘上 `providers.recharge_rate` 折成 CNY：

```
实扣_CNY = actual_cost × recharge_rate      -- 自营站先置 0，倍率不参与
官价_CNY = official_cost × recharge_rate    -- 对照口径同样要折，否则与实扣不同轴
```

- **`recharge_rate` 的语义是「1 个上游计价单位折合多少人民币」**，即上游原值 × rate = CNY。上游若是「1 元充 10 U」，倍率填 **0.1**（而非 10）。人民币计价的站填 1。
- 折算表达式集中在 `upstream_cost_repo.go` 的 `actualCostExpr` / `officialCostExpr`，`CostByAccount` / `CostByDay` / `CostByProvider` / `KeyCosts` 四处共用，**新增聚合必须复用，不要另写裸 SUM**。
- 倍率被写成 0 或负数时按 1 兜底 —— 否则成本会被抹成 0，凭空做高利润。`Create` / `Update` 已做入口兜底，SQL 层再兜一次防手工改库。
- 回归由 `repository/cost_currency_test.go` 锁定。

## 自营站与运营成本

有些上游站点是自己经营的。这类站点的「上游实扣」是左手倒右手，不是真实支出，计入成本会虚增成本、低估利润。因此：

- 在站点设置里打开 **自营** 开关（`providers.self_operated`）
- 该站的上游实扣在所有成本聚合中**计 0**，真实支出改由供应商页「运营成本」弹窗手工录入
- 类别固定四选：买账号 / 订阅费 / 服务器 / 其他，另有自由备注
- 金额**按人民币录入**（`currency` 默认 `CNY`）—— 它要和已折成 CNY 的上游实扣、收益直接相加
- 金额**全额计入发生日**，不做跨期摊销 —— 买一个月的号也记在购买当天，故日趋势可能出现尖刺，月维度总账不受影响
- **仅自营站可录**：非自营站的成本已由上游实扣完整表达，后端硬校验返回 400

两个实现要点：

- **剔除在查询时判定**（`CostByAccount` / `CostByDay` JOIN providers），历史数据零改动。开关一打开立即对所有历史区间生效，关掉也立即回滚
- **用 `CASE ... THEN 0` 置零而非 `WHERE` 过滤行**：过滤会让账号从聚合结果里消失，随即被判成 `cost_matched=false`，误触发下面的「利润被高估 ⚠」告警。自营站成本为 0 是有意为之，不是数据缺失
- 运营成本是**站点级固定成本，不摊到分组**（买号 / 服务器不属于任何分组，且零用量站点没有分组能承载它）。因此分组维度的实扣合计仍等于按供应商口径，但**分组利润合计会偏高**，界面已加口径说明

## 成本同步

上游成本由后台定时任务同步到本地 monitor 库（PostgreSQL），前端查询只读本地库（不实时打上游）：

- 同步间隔默认 **10 分钟**（`cost.interval_minutes`）
- 首次同步会**回补 90 天历史**，耗时较长，通常只需一次；也可在供应商页 💰 弹窗手动「立即同步 / 回补历史」
- 界面展示同步时间、数据新鲜度、key 匹配数（如 `9/9`）；超过 3 个同步周期未更新会高亮告警
- 只存上游 key 名的 `sha256` 指纹，**不存明文 key**

## 成本完整性

上游 key 匹配可能不完整（账号名对不上、供应商站点接口不可用等），系统如实标记而非静默补 0：

- `cost_matched`（账号级）：该账号是否匹配到上游 key，未匹配则成本列显示 `-`
- `cost_complete` / `accounts_missing`（供应商与汇总级）：是否所有有流量的账号都拿到了成本
- 成本不完整时，利润标记 **⚠ 利润上限值** —— 成本偏低导致利润被高估

## 分组成本按用量占比分摊

上游按 key（≈本站账号）计一笔实扣，而一个账号可服务多个分组，实扣本身拆不到分组。故按分组统计的成本是**分摊值**：以各分组在该账号内的原始 token 消耗（裸 `SUM(total_cost)`，不含分组倍率）占比，把账号实扣摊到它服务过的各个分组。

```
账号【厂商X】上游实扣 50，服务两个分组
  分组          收益    成本    利润
  Claude高速     60      30     +30
  Claude备用     40      20     +20
  ────────────────────────────────
  分组合计      100      50     +50
  按供应商      100      50     +50   ← 两个维度的汇总严格一致
```

- 权重用**裸用量**而非收益：收益已含分组倍率，用它当权重会让高倍率分组虚背成本
- 分摊不产生也不吞掉成本，**分组合计 ≡ 按供应商合计**（浮点误差 < 1e-6）
- 免费模型等场景下用量可能全为 0，此时退化为按请求数分摊；请求数也为 0 则均分，保证账号实扣不会无处安放
- 界面顶部有一行显式说明，避免把分摊值误读为上游直接给出的分组账单

## 同步调度（per-provider 错峰）

供应商数据（余额 + 成本 + 上游分组倍率）由**每供应商一个定时器**统一采集（一次登录态全拉完）：

- 刷新开关与间隔在「系统设置 → 自动化与策略」配置（最低 60 秒），保存即热更新免重启
- 同步完成才排下一次，天然防重入防堆积；多供应商初始错峰铺开
- 失败按 15min → 30min → 2h 阶梯退避；登录被拒（4xx，密码错/风控）按 30min → 2h → 6h 冷却，避免反复撞供应商 WAF
- 手动「刷新余额」绕过冷却并清零计数（管理员修好凭据后一键恢复）
- 供应商列表每行有采集健康点：绿=正常，黄=1-2 次失败，红=3+ 次失败或登录冷却

## new-api 会话续期（新旧版自适应）

new-api 自 `v1.0.0-rc.22` 重构了认证：登录改为下发 JWT（TTL 15 分钟）+ `new_api_refresh` cookie（会话 30 天），并新增 `POST /api/user/auth/refresh`。本项目按**登录响应里有没有 `access_token`** 自动判版，用户无需知道上游版本、无需改配置：

| 站点版本 | 会话形态 | 续期方式 |
|---|---|---|
| ≥ rc.22（新版） | JWT + refresh token | 每 15 分钟走 `/api/user/auth/refresh`，密码登录降到 30 天一次 |
| < rc.22（旧版） | 会话 Cookie | 行为与改动前完全一致，401 时整体重登；**永不发送续期请求** |

- 新版凭据复用现有 `access_token` / `refresh_token` / `token_expires_at` 三列，随其余凭据一同加密落库，无需迁移
- 上游的 refresh token 每次调用都会轮换，旧值重放会触发重放检测并**吊销整个会话**，故同一站点的续期加了 per-provider 互斥 + 双重检查（并发采集只会打一次上游）
- 续期失败（凭据被吊销 / 上游降级回旧版）自动清凭据降级密码重登，**不计入登录冷却阶梯**——那是「登录被拒」才该走的路径

## 凭据加密

供应商登录密码 / token / cookie 默认明文存 monitor 库；配置环境变量后自动 AES-256-GCM 加密落库：

```bash
# 生成 32 字节密钥
openssl rand -base64 32
# 启动前设置
export MONITOR_CREDENTIALS_KEY="<上面生成的 base64>"
```

- 未配置时启动日志会告警；配置后新写入自动加密，旧明文数据读取时兼容、下次保存时转加密
- 密钥丢失则已加密凭据不可恢复（须重新录入），请妥善保管

## 稳定性可视化

稳定性页是**盯盘视图**而非复盘视图：默认落在被动统计（真实流量，任何时候都有数据），窗口档位 **5 分钟 / 30 分钟 / 1 小时 / 6 小时 / 24 小时，默认 1 小时**（对齐运维监控，而不是 24 小时复盘口径）。

列表按供应商或分组分块，做成 **色块矩阵**（对齐 sub2api 渠道监控状态页）：一行一个供应商/分组，数字列是整窗聚合，右侧一排方角块是分桶成功率。点色块弹出该行下每个账号的同款行。本页不再提供主动探测 Tab。

**两个口径的差异**

| | 被动统计 | 主动探测 |
|---|---|---|
| 数据源 | 线上 `usage_logs`（真实流量） | 本地 `probe_results`（定时探测） |
| 首字口径 | AVG / P50 / P90 分位数 | 窗口内均值 |
| 成功率 / SLA | **有** —— 成功来自 `usage_logs`，失败来自 `ops_error_logs`（排除业务限制），与运维监控同一公式 | 探测成功率 |
| 采样密度 | 随真实流量 | 默认每 15 分钟一轮 |

选择短于探测间隔的窗口（5 分钟）时，主动探测表会显示提示条说明部分账号尚无样本 —— 空表是采样密度问题，不是账号故障。

**被动 SLA**

`SLA = 成功 / (成功 + 失败)`，失败取 `ops_error_logs` 且排除 `is_business_limited`（余额不足、限额不算服务故障），与运维监控 overview、广场模型指标同一口径。分位数仍然只来自成功请求。被动卡着色用 90 / 70，主动探测成功率仍 95 / 80；都不搬运维监控整站 99.5%——这里按账号盯上游。

**首字延迟为主视觉指标**

首字延迟（TTFT）决定用户「卡不卡」的体感。被动卡主视觉是可用率与趋势条，次要指标写首字 P50 / 时长 P50；主动表仍用窗口均值、分档着色。

分档阈值（`frontend/src/utils/latencyBand.ts`，纯展示决策，改动不牵动后端）：

| 档位 | 首字延迟 | 总耗时 | 呈现 |
|---|---|---|---|
| 优 | < 10s | < 10s | 绿色 |
| 良 | 10–30s | 10–30s | **中性灰** |
| 警 | 30–60s | 30–60s | 琥珀 |
| 差 | ≥ 60s | ≥ 60s | 红色 |
| 无样本 | — | — | 浅灰 `-` |

三点刻意的取舍：

- **首字对齐用量页，而不是再收一层**：2s / 6s / 12s 会把现网常态（P50 3–8s，参考卡 P50 5s / P90 10s）打成黄，颜色常亮即退化为噪音。现档与 sub2api 用量明细 `latencyHealth.ts` 同一量级：10s 内正常，跨过 30s 才该看一眼
- **总耗时保持 10s / 30s / 60s**：总耗时 = 首字 + 输出时长，长回复跑几十秒是正常的。60s 这条线对齐常见客户端请求超时：越过它就不是「慢」而是「失败」
- **「良」档用中性灰而非绿**：四档里两档给绿色会让绿色泛滥，只有落入 fast 档才给正向信号

悬停主动表的延迟数字可看到该列的四档阈值 —— 颜色依据不写在界面上就只能靠猜。

**被动统计是色块矩阵，不是探测表**

顶栏五个 KPI（成功率 / 首 Token P50 / 每秒 Token / 缓存率 / RPM）对当前筛选结果合计。下面每行一个供应商或分组：

| 元素 | 规则 |
|---|---|
| 行首圆点 | **最右非空色块**的分档：≥80 健康 / 50–79 需关注 / <50 异常 / 无流量灰。这不是探测健康状态机 |
| 数字列 | 整窗 SLA、首字 P50、每秒 Token、缓存率 |
| 色块 | 后端细桶（window/60）在前端折成 10–20 格；颜色连续红→黄→绿（`hsl(pct * 1.2)`），空格灰 |
| 悬停 | 色块浮层：时间段、健康分、成功率、首 Token AVG/P50/P90、每秒 Token、缓存率、错误率、RPM、请求时长 AVG/P50/P90 |
| 点击 | 点色块打开弹窗：该桶成功率 + 该行下每个账号的同款色块行（高亮被点的格） |

- 色块分档 80 / 50 对齐运维监控图例，和主动探测成功率 95 / 80 不是同一套
- 窗口内 **只有失败、没有成功** 的账号仍出现（两表 FULL OUTER JOIN）
- 探测接口仍在，稳定性页不再入口

**主动探测的行首综合评级色点**

主动表账号名左侧的色点仍是「这一行该不该看」的单一信号，取**首字延迟 / 成功率 / 健康状态三者中最差**的那个，而非加权平均。

- 绿 = 各项正常；琥珀 = 有指标接近阈值；红 = 有指标已超阈值；灰 = 窗口内无样本
- 成功率阈值 95% / 80% 与该列文字着色对齐
- **人工停用（disabled）归灰而非红** —— 停用是「不在观测范围内」，不是故障

**归属供应商**

两个口径的归属都取 `provider_accounts` 关联表的**现值**，而非 `probe_results.provider_id` 快照 —— 后者是探测发生时的归属，账号事后被别家「抢」走时历史行仍带旧 id，按它分组会让同一账号在「每账号一行」的表里裂成两行。未关联账号落入「未归属」桶，可单独筛选，不会凭空消失。

窗口参数走 `minutes`（旧 `hours` 仍兼容，按 60 倍换算），上限 30 天。

## 模型检测（渠道指纹）

买到的「Claude」不一定是 Claude。市面上同时存在官方 Max 订阅号池（OAuth 反代）、官方 API Key 直连、AWS Bedrock、Kiro / Vertex 反代，以及把别家模型套上 Anthropic 外壳的伪装渠道。本页对单条上游连打一组请求，从可观察行为反推它背后是什么。

### 两个结论是正交的，必须分开

页面同时输出**渠道分类**与**真实性评分**，因为它们回答的是两个不同的问题：

| | 渠道分类 | 真实性评分 |
|---|---|---|
| 回答 | 这条链路是谁在承载 | 后端到底是不是真 Claude |
| 判据 | 消息 id 形态、限流头、注入痕迹、人设自述 | 签名完整性、参数校验、协议严格性 |
| 典型反例 | 号池注入 Claude Code 人设 —— 这是**分类证据**，不是造假证据 | 一条「干净的官方直连」也可能被中间人换成国产模型 |

把两者揉成一个分数，就会出现「自称 Claude Code 所以扣分」这种荒谬结论 —— OAuth 号池必须注入 CC 人设才能用订阅额度，那恰恰说明它是真号池。

### 组合证据，不看孤证

网关能改写的字段远比想象中多：`toolu_` 前缀、`msg_` 前缀、`service_tier`，都可以照抄官方形态。因此每条证据只往某个类别加权重，最高分者胜出，并要求领先次高分 3 分以上才算高置信度。少数几乎没人伪造的强指纹（`req_vrtx_`、`claude#` 签名前缀、`anthropic-ratelimit-unified-5h-*`）单独出现即给高置信度。

`msg_bdrk_` 不在此列：实测有渠道顶着它，而模型回显、签名内部编码、篡改报错三处全是第一方 Anthropic 形态 —— 贴一个前缀字符串的成本太低。因此它单独只值 2 分（够不到分类阈值），要由跨项审计凭独立旁证（`x-amzn-*` 响应头、`anthropic.claude` 形态模型回显、`tooluse_` 工具 id、Bedrock 形态签名或错误报文）补足 3 分才成立。

同一个指纹被观察到多次只计一次分 —— 两个工具调用都返回非官方 id 是一条证据的重复观察，不是两条独立证据。

### 跨请求审计：单项检测看不见的矛盾

有几类伪造只在**跨请求比对**时才暴露，单个检测项拿不到别的项的响应。因此在出判定前加一道零请求的审计，回读所有已完成项的响应：

- **缓存门槛**：总输入（`input + cache_read + cache_creation`）低于模型的最小可缓存前缀（Opus 5 = 512 tokens）却报缓存命中，物理上不可能 —— 短于门槛官方静默不缓存。
- **usage 守恒**：`input_tokens=0` 却有输出；若同时 `cache_read>0`，说明输入被整体记进了缓存读取（字段错位）。
- **thinking 自洽**：带签名的 thinking 块**全程**没有正文。注意单次空正文是 adaptive 的合法形态（真 Bedrock 渠道也这样返回），只有整轮从未出现过任何思考正文才定罪。
- **平台形态交叉一致**：消息 id 内核、模型回显、签名内部编码、篡改报错格式四个维度各归一出一个平台族，真渠道必然同向。签名内部编码是未公开实现细节，因此这一项只作低权诊断线索，解析失败静默跳过；另外三个维度不依赖它。

前三项是基于公开协议的硬判据，命中即封顶真实性评分。

### 真实性评分的权重来自「伪造成本」

- **签名完整性 40 分**（权重最高）：原样回传 thinking 签名能续写、改一个字符必须被拒。只有真正持有 Anthropic 签名密钥的后端（含 Bedrock / Vertex）能同时做到，逆向实现要么两边都放行，要么根本无法续写。
  > 反过来说，**签名跨账号 / 跨端点重放报 `Invalid signature` 是设计内行为**，不是造假证据 —— 签名绑定模型与端点，第一方与 Bedrock 之间本就互不通用。
- **参数校验 15 分**：`thinking.budget_tokens=200`、未知顶层字段、`max_tokens=0` 都应被官方网关拒掉。逆向实现与 OpenAI 格式转换层普遍照单全收。
- **max_tokens 硬上限 10 分 / 工具调用 10 分 / SSE 状态机 10 分 / count_tokens 一致性 5 分**，能力项（图片、PDF、Schema、缓存、采样熵、thinking 梯度）各 5 分。

**封顶规则**：观察到造假硬证据（篡改签名被接受、`max_tokens` 被忽略、系统提示里出现非 Claude 品牌词、全部非法参数被放行、跨请求审计的前三项）时总分封顶 30 并标记「疑似伪装」。它是**否决项**而非扣分项 —— 一条渠道在其他项上表现再好，也盖不住「后端不校验签名」这件事。

### 失败分级，临时故障不当能力否定

单项结论分五态：观察通过 / 协议失败 / 目标不支持 / 证据不足 / 结果可疑。网络错误、429、5xx 一律记「证据不足」；adaptive 模型本轮合法跳过 thinking、返回 `redacted_thinking`、网关未透传 `count_tokens`，都记「不支持」或「证据不足」，不判负。号池会轮换账号，同一把 key 两次结果可能漂移，所以结果落库留痕，**稳判需要多轮对照**。请求失败（网络错误 / 超时 / 429 / 5xx）可在本轮作业上单独重试，协议失败不提供重试——再打一遍不会得到新证据。

### 成本与凭据

高成本项（采样熵 10 次、thinking 梯度 3 次、Prompt Cache 3 次）默认关闭，勾选时二次确认。页面上的「并发」是**全局在途检测项上限**（默认 3，最高 10）：无 `Requires` 的项并行执行，作业快照里正在跑的格子为「执行中」。`ping-again` / `sig-tamper` / `count-tokens` 等声明了前置依赖的项仍等前置完成，避免第二次请求命中并发那一路写的缓存、或签名篡改拿不到上一档的 thinking 块。撞限流由运营自己权衡。

API Key 只在进程内用于发请求：不入库、不进报告。响应原文在解析**之前**就做脱敏，否则「渠道把 key 回显在响应里」会绕过只擦 `raw` 的做法。历史表只存 `target_fp`（`sha256(base_url + key)` 前 16 位），既能把同一条渠道的多次检测串成时间线，又不留下可用的凭据。

## 表格排序

收益统计、分组倍率、稳定性、授信台账等表格支持点表头排序：点同列切换升/降序，点新列从升序起（无「取消排序」第三态）。

- **空值恒排末尾**，升序降序都是 ——「没有数据」不是「值最小」，不该在升序时挤到有数据的行前面
- 数字按数值比，其余按自然序（`acc2` 排在 `acc10` 前），大小写不敏感
- **未点任何表头时保留后端默认序**，例如收益统计的「(未归属)」桶在后端恒排最后；主动点了某列才按真实值排（那时「未归属」按其真实收益插到中间是对的，藏在最后反而是信息损失）
- **上游站点列表：余额方式为「不监控」（`balance_type='none'`）的站点恒排最后**，与排序键和升降序无关。这与「空值恒末尾」是两件不同的事 —— 缺值是「这个字段没数据」，不监控是「这个站点整体不参与运营关注」，后者即使余额字段有值（手动录入过）也该沉底。判据刻意不含 `manual`：人工维护余额的站点仍在关注范围内，照常按余额排序
- **授信台账走后端排序**（其余表格前端本地排）：它有分页，本地排序只能排当前页，「这 20 人里敞口最大的」会被误读成「敞口最大的」，授信决策不能建立在这种误读上。排序列经白名单校验，非法值静默回退默认序

## 时区

「今日」按 `timezone` 配置的本地时区取 UTC 边界（须与 sub2api 主站一致）。

## 授信台账（人工记账）

替客户垫付（先在 sub2api 后台充值、事后收款）的应收账本。

> **⚠️ 这是一本人工台账，不是自动对账系统。**
>
> 本模块**永不写上游**，台账**不对账**：
> - 实际充值由运营方在 sub2api 后台手动执行，系统只记录「我垫了多少」；
> - 不识别 PG 充值流水，线上余额也不会写进敞口；
> - **例外：** 对生效客户只读扫描 `users.balance`，缓存到客户档案供列表展示，并在跌破阈值时通知运营提前垫付；
> - 因此**账目准确性完全取决于录入纪律** —— 垫付后忘了记一笔，台账就与现实脱节，系统无从察觉。

为什么不自动化：sub2api 强制会话绑定（JWT 的 `bnd` = sha256(客户端 IP + UA)），服务端拿用户 token 直连必然校验失败，且失败时会撤销该用户**整个会话家族**、把人从浏览器踢下线。代价远大于收益。

### 建档

客户唯一口径是 `sub2api_user_id`，**建档时从线上 users 表拉列表直接选人**，避免手打错一个数字就把台账永久挂到别人身上（本模块无对账机制，挂错了系统无从察觉）。

- 下拉项展示 `#id 邮箱 + 余额 + 状态`，搜索同时匹配 id 与邮箱；**已建档的用户禁选**（应去列表编辑其档案）
- 不过滤 admin 与 disabled 用户：授信对象是「谁欠钱」与角色无关，而欠钱被停号的用户往往正是要追的那个
- 选中后自动回填邮箱与客户名（不覆盖已填内容）
- **建档后 user_id 不可改** —— 改了等于换了个人，历史台账会挂错，编辑态渲染为只读
- **线上库不可用时表单降级为手填输入框**：PG 挂了就建不了档是不可接受的

### 额度语义：循环授信

授信额度封顶的是**未回款的垫付余额**，不是「本月用了多少」：

```
已用额度（敞口） = Σ垫付 − Σ回款
可用额度         = 授信额度 − 已用额度
```

敞口允许为负，表示客户预付。币种统一 USD。

- **只追加账本**：分录不可改不可删。记错了写一笔等额反向分录（`reversed_of` 指向原分录），审计轨迹完整
- **敞口一致性**：每次写入在同一事务内用全量 `SUM` 重算，而非增量 `±amount` —— 单连接只串行化写、不保护读-改-写，且 float 增量会累积误差。管理端另有「重算」按钮兜底，幂等
- **分级告警**：敞口达额度 80% / 100% 各推一次通知（复用现有钉钉 / 飞书 / Telegram 渠道）。**边沿触发**：同档内不重复打扰，跌回低档静默改写闩锁，再次升档才重新告警。闩锁存 `customers.alert_level` 而非内存。`credit_limit ≤ 0`（未授信）任何敞口都不告警
- **客户线上余额提前告警**：每 5 分钟只读扫描生效客户的 `users.balance`（启动时先扫一轮）。全局默认阈值 + 客户覆盖；跌破立即通知，持续偏低每小时补催，回升到阈值上方静默重新武装。闩锁存 `customers.user_balance_alert_level` / `user_balance_alert_at`。扫描结果是缓存，不是账本
- **不阻断**：超额只告警，不影响客户用量

### KYC 实名资料

授信前需掌握交易对手身份，个人 / 公司两套字段集，纯文字录入（不做文件上传）。

两个入口共用同一份表单与校验：

| 入口 | 路径 | 说明 |
|------|------|------|
| 管理端代录 | 授信页 → 客户行「资料」 | 查看 / 代客录入 / 审核三合一 |
| 客户自助 | `/embed/kyc?token=…&user_id=…` | 由 sub2api 以 iframe 嵌入，客户自行填报 |

状态流转 `draft → pending → approved \| rejected`，驳回后可重新编辑再提交；**通过审核即锁定**，客户无法自改，变更走管理端。

安全约束：

- 姓名 / 证件号 / 地址 / 银行账号等 PII 全部加密落库（`_enc` 后缀列）。**加密用随机 nonce，同一明文两次结果不同 —— 这些列绝不能进 WHERE / ORDER BY / UNIQUE / INDEX**
- 未配置 `MONITOR_CREDENTIALS_KEY` 时 PII 明文落库，启动日志会告警。**明文身份证号的严重性高于明文凭据**，生产环境务必配置
- 读 KYC 用 `Open()` 而非 `MustOpen()`：解密失败必须报错，不能像凭据那样静默返回空串 —— 身份信息不可再生
- 嵌入页客户身份**只取自会话上下文**，请求体里连 `user_id` 字段都不存在；URL 上的 `user_id` 仅供后端与 token claims 比对。改 URL 换不出别人的会话
- 嵌入端**永不引入 Cookie 鉴权**：CSRF 安全性完全依赖「凭据只在 `Authorization` 头里」
- 客户侧接口返回独立裁剪的 DTO，`admin_note` 与 `reviewed_by`（内部审核人）永不外泄
- 嵌入页可被哪些 origin 嵌套由 CSP `frame-ancestors` 控制，路径为**显式白名单**（`middleware.embedPagePaths`）。**新增 `/embed/*` 页面必须同步登记**，刻意不用前缀通配

## 生图 / 生视频

嵌入 sub2api 的自助生成页，让用户用**自己的 API Key** 调网关生成图片与视频。四种模式：文生图、图生图、文生视频、图生视频。

### 一切设计都绕着「钱」

上游有三条硬规则，页面的每个取舍都源于它们：

1. **视频费用在提交成功那一刻即计入，内容审核拒绝也不退还。** 720p×15s 是 $1.05，约等于 52 张标准图。
2. **图片计费按最长边判定档位**（≤1024 为 1K，≤2048 为 2K，更大为 4K）。`2560x1440` 按 4K 计费而非 2K。
3. **实扣 = 单价 × 数量 × 倍率**，且单价可被分组覆盖。三个因子缺一，页面报价就会与账单对不上。

由此推出：

- **任务必须落库。** 内存会话 30 分钟就过期、进程重启即失效，而任务记录是「钱花在哪」的凭证。用户刷新 iframe 不能让已付费的任务消失。
- **提交必须带幂等键。** `client_request_id` + `UNIQUE(sub2api_user_id, client_request_id)`，命中直接复用既有任务而不是报错——报错反而诱导用户再点一次，那就是二次扣费。
- **先落 pending 再打上游。** 顺序反过来时，落库失败就产生一笔查无实据的支出；现在最坏情况只是多一条 failed 记录，可对账。
- **网关调用不重试。** 与 `probe_service` 的重试纪律相反：那是只读探测，重试无副作用；这里网络超时后上游任务可能已创建成功，重试等于二次扣费。
- **视频强制二次确认**，弹窗里写清预估金额。图片不需要——单张两三分钱。
- **上游 4xx 必须当终态。** 轮询视频状态时的 400 是「审核拒绝」，永远不会转成功，继续轮询只是浪费。而且钱已经扣了，UI 必须让用户分清「没扣钱的参数错误」与「已扣钱的审核拒绝」。

### 预估费用必须复刻上游的完整定价链

页面要在用户按下按钮之前给出「大约扣多少」，而上游没有试算接口，只能本地算一遍。**一期只算了「标准单价 × 数量」，漏掉了后两个因子，配了倍率或自定义价的分组全部报错价。**

完整口径（源自 sub2api `billing_service.go` 与 `openai_gateway_usage.go`）：

```
图片单价 = groups.image_price_{1k|2k|4k}  非 NULL 时优先
         : 模型标准档位价
视频单价 = groups.video_price_{480p|720p|1080p}  非 NULL 时优先
         : 模型标准档位价（USD/秒）

倍率 = groups.image_rate_independent ? groups.image_rate_multiplier : 有效分组倍率
      （视频用 video_rate_* 那一组）
有效分组倍率 = user_group_rate_multipliers 的专属值 : groups.rate_multiplier
```

三处容易再次踩空的地方：

- **`image_price_*` 用指针而非 float 承接。** `0` 是合法的自定义价（免费档），用零值表示「未配置」会让免费分组回落到标准价。
- **`grok-imagine-image-quality` 是分档价**：1K $0.05 / 2K $0.07。一期写死 $0.07，1K 档报价高了 40%。
- **高峰倍率不叠加到图片和视频。** sub2api 的 `computePeakAwareMultipliers` 只对 token 计费乘 `PeakMultiplierAt`，图片走独立分支。跟着叠会让报价凭空变高。

复杂度全部收敛在后端：`ClassifyModels` 下发的是**已折算的最终单价**（`price_by_tier`），前端只做「单价 × 数量」。这两半过去各算一部分，正是报价与账单对不上的根因。

### `size` 与 `aspect_ratio` 是两条互斥的路径

一期的结论是「Grok 图片模型静默忽略 `size`，恒输出 1024×1024」，据此禁用了所有尺寸控制，用户只能生成 1:1 的图。

**这个结论是错的。** 真相是 sub2api 网关的 `sanitizeGrokMediaForwardBody`（`grok_media.go`）在转发 Grok 图片请求前**主动删掉 `size` 字段**——所以传它当然没用。Grok 认的是 xAI 原生的 `aspect_ratio`（14 档，含 `auto`）+ `resolution`（`1k`/`2k`），网关对这两个字段原样透传。

| 模型族 | 尺寸参数 | 计费档来源 |
|---|---|---|
| `grok-imagine-*`（图片） | `aspect_ratio` + `resolution` | `resolution`（1k → 1K 档，2k → 2K 档） |
| `gpt-image-*` | `size`（真实 `宽x高`） | 最长边 |

**两套参数绝不能同时出现在一次请求里**：body 里只要带 `size`，网关就走删除分支，实际生效的是哪个取决于上游实现细节。因此 `MediaSizeMode` 被建模成显式枚举而非 `SupportsSize bool`——布尔只能表达「支不支持」，表达不了「该用哪一套」，而后者才是真正的分歧点。

`media_gateway.go` 的 `applyImageSizeParams` 是两条提交路径（JSON 与 multipart）共用的唯一装配点。它们过去各写一遍，正是 `size` 只在其中一条被处理的温床。

### 静默降级的模型必须按降级后的价报

sub2api 的 `NormalizeGrokMediaModelForEndpoint` 会替换模型且不留任何痕迹：

| 请求 | 上游实际使用 | 计费依据 |
|---|---|---|
| `grok-imagine` 走图片端点 | `grok-imagine-image-quality` | 后者 |
| `grok-imagine-video-1.5` **无参考图** | `grok-imagine-video` | 后者（便宜） |
| `grok-imagine-video-1.5` **有参考图** | 1.5 本身 | 1.5（贵） |

一期把这两个模型当「陷阱」整个过滤掉了，代价是用户根本用不了它们。现在的做法是放行 + 在 `mediaModelSpec.DowngradesTo` 里登记降级关系：

- `EstimateCostTicks` 按降级后的模型取价——否则文生视频选 1.5 会显示 $0.64 而实扣 $0.40，页面在骗人
- 前端在会降级的组合上显示明确提示，让用户知道「你选的不是你得到的」

### 产物转存到对象存储

一期的取舍是「只存元数据」：图片走 b64 随提交响应返回一次就丢弃，视频只存 `request_id` 由后端实时代理。代价是刷新页面图片就没了，视频过了上游保留期连后端也取不到——用户付了钱却留不住产物。

现在产物落 Cloudflare R2，前端拿到的是不需要认证、不会过期的普通 URL。

**图片同步转存，视频异步。** 图片单张几百 KB，转存耗时相对生成本身（5-10 秒）可忽略；而「视频已完成」是在用户轮询任务列表的同步请求里被发现的，在那里传几十 MB 会把一次本该几十毫秒的列表查询拖成几十秒。

`media_archiver.go` 的几条纪律：

- **转存失败不让任务失败。** 钱已经扣了、产物已在手上，失败只该降级成「本次会话内可见」，而不是把一次成功的生成标成失败。前端据 `storage_status` 回落到 inline / 代理路径
- **部分成功也标 `failed`。** 标 `stored` 会让前端只显示已转存的那几张，用户以为少生成了——而钱是按全部张数扣的
- **用 `context.Background()` 而非请求 ctx。** 转存要活过发起它的那次 HTTP 请求；挂在请求 ctx 上会在响应写完的瞬间被 cancel，表现为「转存总是失败」且日志里只有一句 `context canceled`
- **`inflight` 去重 + 信号量限并发（2）。** 列表每 5 秒刷新一次而 `storage_status` 在转存完成前一直是 `pending`，不去重的话同一个视频会被重复下载上传好几遍
- **后台 goroutine 自己兜 panic，`enabled()` 校验全部依赖。** 那里没有 gin 的 recover 中间件，一次 nil 解引用就会带走整个进程——而转存失败本该只是一条日志。这条是被单测逼出来的：最初 `enabled()` 只查 `uploader`，装配漏了 repo 时后台直接崩
- **重启补扫。** 转存中途重启会留下一批 `storage_status='pending'` 的孤儿，它们既不自愈也不会被任何用户操作触发，启动时捞一遍是唯一出路

产物单独一张 `media_artifacts` 表而非给任务加列：一个图片任务最多 4 张图，塞进任务行会逼出 `result_url_2/3/4`。外键带 `ON DELETE CASCADE`，但 R2 上的对象不同步删——让「删记录」这个高频操作依赖一次跨境网络调用不划算，对象清理交给桶的生命周期规则。

未配置 R2 时整套退化回一期行为，生成本身不受影响。

### 模型用显式 allowlist，不用前缀通配

`/v1/models` 会返回一些「看起来能用」但行为特殊的模型。前缀匹配（`grok-imagine-` → 图片）会把它们全放进下拉框，用户选中后要么收到 404、要么被静默换成别的模型。登记表在 `service/media_catalog.go`，这是刻意的「不 DRY」。

| 模型 | 实际行为 | 处置 |
|------|---------|------|
| `grok-imagine-edit` | 图片编辑接口 404 | **不登记** |
| `grok-imagine` | 走图片端点时被映射成 `grok-imagine-image-quality` | 登记 + `DowngradesTo` |
| `grok-imagine-video-1.5` | 无参考图时降级为 `grok-imagine-video` | 登记 + `DowngradesTo`（限 `t2v`） |

**一期把后两个也当陷阱整个过滤掉了**，理由是「`grok-imagine` 视频接口 404」——那个观察只对视频端点成立，图片端点是通的；而 1.5 在图生视频时真正生效。代价是用户根本用不了这两个模型。现在的做法是放行 + 登记降级关系，由预估逻辑按降级后的模型报价（见上文）。

`1080p` 同理：一期以「上游明确返回 400」为由拒掉，但那是对 `grok-imagine-video` 的观察，sub2api 的计费表为 1.5 保留了独立的 1080p 单价（$0.25/s）。若某组合确实不支持，上游返回的是**参数错误 400、不扣费**，代价远小于永久藏起一个能用的档位。

### 能力门禁：图片是开关，视频是平台

两者判定路径不同，容易搞混：

- **图片**：`groups.allow_image_generation` 布尔列，关闭时上游返回 `403 permission_error`
- **视频**：**没有** `allow_video_generation` 这一列。判据是 `groups.platform == 'grok'`（或 `composite`），非 grok 平台的视频接口直接 404（sub2api `routes/gateway.go` 的 `videoGenerationHandler`）

### 明文 Key 的流向

后端从只读 PG 按会话用户查出该用户的 `api_keys.key`，**仅在「后端 ↔ 网关」这一段的内存里存在**：

- 不进任务表（只存 `keyidentity.Fingerprint` 指纹，用于事后归因，且 key 轮换后仍可比对）
- 不进日志（错误一律过 `redactError`，有专门的单测钉死「错误信息不含明文 key」）
- 不进响应（`MediaKeyView` 类型里根本没有明文字段，掩码在 service 层完成，让 handler 忘了掩码这种失误在类型层面不可能发生）
- 每次调用重新查 PG 而不缓存：key 可能被随时禁用，缓存会让已撤销的 key 继续可用

### 代理端点只剩兜底作用

转存启用后，前端渲染产物的优先级是：**R2 URL → 本次会话的 data URI → 后端代理**。第一项覆盖绝大多数情况，后两项只在转存未启用或失败时才走到。

代理端点仍然保留，因为视频转存是异步的：产物完成到转存完成之间有一段窗口期，此时只能靠代理播放。它也是 R2 未配置时的唯一出路。

**为什么代理而不是把上游 URL 丢给浏览器：** 视频下载端点强制要求 `Authorization` 头，而 `<video src>` 发的是不带自定义头的裸请求，必然 401；前端也拿不到明文 key（不该拿到）。xAI 的图片 CDN 直链则是国内常不可达且会过期。

**代理端点的两道防线**：归属校验写在 SQL 里（`WHERE id=? AND sub2api_user_id=?`），查不到统一 `ErrNotFound`，不区分「不存在」与「不属于你」以防枚举；图片目标域名走白名单，因为 `result_url` 来自上游响应而非本站构造，无白名单时这个端点就是 SSRF 跳板。

### 视频状态被动刷新，不起后台轮询

前端每 5 秒拉一次任务列表，后端在返回前顺带刷新在途视频任务（单次上限 5 个）。

不做后台 goroutine 的理由：需要常驻、需要重启恢复、还要处理「用户早就不看了但任务还在跑」的资源浪费。任务状态只有用户在看列表时才有意义——挂在列表查询上零常驻成本，用户关页面期间的状态变化会在下次打开时自然补齐。

### 图生图的参考图：Grok 与 gpt-image 字段不同

两端共用 `/v1/images/edits`，但 JSON 契约按模型族分叉：

| 模型族 | 字段 | 单张示例 |
|---|---|---|
| Grok | 嵌套 `image.url` | `{"image":{"url":"https://…"}}` |
| `gpt-image-*` | OpenAI JSON：`images[].image_url` | `{"images":[{"image_url":"https://…"}]}` |

把 Grok 的 `image.url` 原样转给 gpt-image 会立刻 400：`images[].image_url is required`。装配点在 `applyEditImages`，按 `MediaSizeMode` 分流——那已经是「OpenAI 格式 vs Grok 格式」的分界。

### 图生视频的参考图

上游只认 JSON 里**嵌套**的 `image: {"url": "..."}` 且要求公网可达（传 multipart 直接 415）。产物转存启用后，本次会话刚生成的图片有了长期可用的 R2 URL，可以直接粘回来当参考图；也可以填任意外部 URL。

**字段形状是嵌套对象，不是顶层 `image_url`。** 这一点踩过坑：供应商文档（kaola-doc `grok-media.md`）原写作顶层 `image_url`，本站照此实现并写了断言该形状的单测，全链路"自洽且通过"，但线上产物完全不参考图片。根因是上游对未知字段静默丢弃——HTTP 200、`request_id` 照发、**费用照扣**，只是生成时退化成了文生视频，没有任何错误信号。

定位靠的是对照实验（同模型、同参考图，只改字段形状），肉眼比对首帧：

| 请求体 | 参考图（黄色小鸭） | 实际产出 |
| --- | --- | --- |
| `{"image_url": "…"}` | 同一张 | 晨雾湖景，与图无关 |
| `{"image": {"url": "…"}}` | 同一张 | 黄色小鸭，忠实还原 |

`grok-imagine-video` 与 `grok-imagine-video-1.5` 表现一致，模型版本不是变量。另注：参考图生效时输出宽高比跟随参考图（1:1 图在 480p 档输出 544×544），而非 `resolution` 隐含的 16:9。

**留下的教训**：与上游对接时，"字段名和供应商文档一致 + 单测通过"不等于契约正确。静默丢弃未知字段的上游会把错误一路放行到用户面前。对**扣费且无错误码**的接口，验收必须落到产物本身，不能停在 HTTP 200。kaola-doc 与 `usage-docs.md` 已同步订正。

### prompt 不加密

prompt 是用户刚输入的创作描述、非 PII，且要在任务列表里展示与检索。KYC 的身份证号加密是因为它不可再生、泄露不可逆；prompt 不适用同一标准。代价是运维可见用户 prompt。

### 费用只记在任务表

`cost_in_usd_ticks`（1 tick = 1e-10 USD）记录上游实扣，页面展示单次与预估对照，**不接入现有的成本 / 收益体系**。那套体系算的是运营方对上游的支出，而生图花的是终端用户自己的钱，混进去会让利润口径失真。
